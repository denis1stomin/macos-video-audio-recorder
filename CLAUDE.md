# RecRex — Project Context

## Goal
Build a macOS tool to record screen and audio (system sound and/or microphone).

## Status
Initial v1 scaffold implemented: SwiftUI app with the documented window flow (configure → select source → recording/processing), ScreenCaptureKit + AVAssetWriter capture engine (video, system audio, microphone as separate tracks, 1.5h segment rollover, pause/resume, auto-stop on window close), App Sandbox entitlements, a normal committed `RecRex.xcodeproj` (see decision log — briefly generated via XcodeGen, then converted back to a standard committed Xcode project), unit tests for the pure logic (file naming, segment scheduling, button label), and a GitHub Actions workflow that builds and runs the unit tests directly against the committed project. Builds and launches successfully locally (Xcode 26.5 / macOS 26 SDK). Both the `Build and Test` and `CodeQL` GitHub Actions workflows have run green on `main` (repeatedly, including as part of the `v0.9.0-rc.1`/`rc.2` release prep), and the `Release` workflow has successfully built, packaged, attested, and published `v0.9.0-rc.1` as a GitHub Release. Confirmed working end-to-end against a real live meeting app (Yandex Telemost) — screen + audio capture succeeded — though that same real-world testing surfaced two product issues now tracked as open decisions below (large output file size, echo when mixing system audio + microphone).

## Open decisions (not yet made)
- User-facing quality picker (High / Medium / "Optimized" or similar wording): not yet built. The *default* itself was tightened (see decision log below) in response to the ~2.4 GB/70-minute file size found in real-world testing, but there's still no user-facing control over it — exact levels/wording still open. See `RELEASE_NOTES.md` Known issues.
- Echo when recording system audio + microphone together: likely the microphone acoustically picking up system audio output (e.g. no headphones during a call), but unconfirmed. **Next step, pending user testing:** check whether the echo persists with headphones on — if it goes away, that confirms acoustic feedback and points to acoustic echo cancellation on the microphone path (e.g. `AVAudioEngine`'s `inputNode.setVoiceProcessingEnabled(true)`); if it persists with headphones, AEC won't help and the real cause needs separate investigation (e.g. the meeting app duplicating audio into both mic and system-audio streams). Full detail, including why the AEC path is nontrivial (no AEC option in ScreenCaptureKit's own mic capture; `AVAudioEngine` voice processing has known channel-count and input/output-device-mismatch fragility on macOS; would need a second capture pipeline synced with the existing `SCStream`-driven `AVAssetWriter` session), is in `RELEASE_NOTES.md` Known issues.

## Decision log
- Artifact hosting/distribution: **GitHub Releases**, wired up via `.github/workflows/release.yml`. Triggers on pushing a `v*` tag (or manual `workflow_dispatch` with an existing tag), archives the `Release` configuration as a universal binary (`ARCHS_STANDARD` already covers arm64+x86_64) ad-hoc signed (`CODE_SIGN_IDENTITY="-"`, no Developer ID needed — consistent with the sandbox/signing decision below), zips the `.app`, and publishes a GitHub Release with that zip attached. A tag containing a hyphen (e.g. `v0.1.0-rc.1`) is published as a prerelease; a plain `vX.Y.Z` tag is a full release. First cut as `v0.9.0-rc.1`; `v0.9.0-rc.2` adds no app changes, only the release-pipeline/CodeQL/attestation work below.
- Binary provenance: since there's no Apple notarization (and thus no Apple malware scan) and GitHub has no built-in binary/malware scanner for release assets, the release workflow attests the zip with **`actions/attest-build-provenance`** (GitHub's free SLSA-style build provenance) so downloaders can verify with `gh attestation verify` that the artifact really was built by this repo's public workflow from the tagged commit. This proves supply-chain integrity, not the absence of malware — a real limitation until/unless notarization is added later.
- App type / language / SDK: **Native Swift app with a regular Dock icon** (SwiftUI/AppKit) — not a menu-bar-only background app; it shows in the Dock and Cmd+Tab switcher like a normal app. Uses ScreenCaptureKit/AVFoundation for capture. macOS's own built-in recording indicator (in the system menu bar) covers the "capture is active" signal — the app doesn't need its own menu bar icon.
- v1 capture scope: **all combinations** of video, system audio, and microphone are supported, including audio-only recordings that mix system audio and microphone together.
- Platform/format: target the **latest macOS** (current ScreenCaptureKit/AVFoundation APIs), output **MP4 (H.264)**.
- Source control hosting: **GitHub** (already set up — `origin` is `git@github.com:denis1stomin/macos-video-audio-recorder.git`).
- CI: **GitHub Actions** with a macOS runner, building (and later testing) on every push/PR. Must use the `macos-26` runner image (not `macos-15`) since that's the first GitHub-hosted image with Xcode 26.x / the macOS 26 SDK — matches our `MACOSX_DEPLOYMENT_TARGET = 26.0`. `macos-15`'s Xcode only supports deployment targets up to 15.5.99, so it can't build this project (hit this the hard way: first CI run on `macos-15` produced a deployment-target-out-of-range warning).
- Packaging: **universal binary** (arm64 + x86_64) in a single app bundle, so one download works on both Apple Silicon and Intel Macs.
- Pause/resume: pausing stops **both video and audio** capture (no dead air or frozen-frame gap in the output), and the processing window shows a clear paused state (timer stops, button/label changes to indicate paused).
- Icon: **finalized** — the app icon in `RecRex/Resources/Assets.xcassets/AppIcon.appiconset` is the icon going forward, not a placeholder. No menu bar icon is needed (see the ScreenCaptureKit/macOS-indicator note above).
- Video quality: **no user-facing quality picker in v1** — encode with a sane default via hardware-accelerated VideoToolbox encoding, keeping the UX to the documented two-click flow. Can revisit as an optional advanced setting later (see the open decision above). The default itself, in `RecordingManager.swift`, was **tightened after real-world testing found a ~2.4 GB/70-minute full-screen recording** at the original "native resolution, VideoToolbox's own automatic bitrate" settings: (1) resolution capped at 1080px on the longer edge (`maxVideoDimension`) — a meeting doesn't need native 5K/6K display pixels, and 1080 was chosen over an initial 1920 for a further size cut — scaled proportionally so aspect ratio (and therefore no letterboxing) is preserved, still derived from the real `SCContentFilter` content size rather than a guessed scale factor; (2) frame rate capped at 30fps (`videoFrameRate`) via `SCStreamConfiguration.minimumFrameInterval` — ScreenCaptureKit otherwise delivers frames at the display's own refresh rate (up to 120Hz on ProMotion) regardless of on-screen motion; (3) an explicit average bitrate (`averageVideoBitRate`, ~0.06 bits/pixel/frame, clamped to 1.5–8 Mbps) instead of VideoToolbox's uncapped default, plus the H.264 High profile for better compression efficiency at the same quality. Audio (`audioSettings`) was tightened the same way — mono instead of stereo, 64 kbps instead of 128 kbps AAC — since meeting content is almost entirely speech and putting all the bits into one channel keeps quality closer to transparent than splitting them across two would at the same total bitrate. Not yet re-validated against a real recording for the resulting file size/quality trade-off.
- Encoding approach: encode **on the fly** during capture (ScreenCaptureKit sample buffers → `AVAssetWriter` with hardware H.264 encoding via VideoToolbox), not raw-capture-then-postprocess — hardware encoding is low-overhead and runs in parallel with the video-meeting app's own CPU/GPU usage.
- Permissions flow: on first use, RecRex triggers the **native macOS permission prompt** for both Screen Recording and Microphone (screen recording implicitly, by calling `SCShareableContent.current`; microphone explicitly, via `AVCaptureDevice.requestAccess(for: .audio)`) so the user can grant access right there without leaving the app. Only once a permission has actually been **denied** does RecRex fall back to its own alert, which simply **notifies the user what's wrong and how to fix it** (i.e. points them to System Settings to re-enable it) — no attempt to auto-open System Settings or otherwise work around a denial beyond that notice.
- System audio capture scope: when recording a **specific app window**, capture system audio only from that app (not all system sound), and always **exclude the recorder app's own audio output**. When recording the **whole screen**, capture all system audio (no single app to scope to). Microphone audio, when enabled, is captured **in addition to** whichever system audio is captured.
- Mixing mic + system audio: kept as **separate audio tracks in the output container** (not mixed down to one track) — lets the user (or downstream editing tools) control/mute each source independently.
- File naming: `Recording YYYY-MM-DDTHH-MM-SS.mp4` — ISO 8601 date/time (24-hour), with hyphens instead of colons since `:` is unsafe/reserved in macOS filenames. On a name collision in Downloads, append a Finder-style duplicate suffix before the extension: ` (2)`, ` (3)`, etc.
- Multi-display selection: in "record whole screen" mode, show a preview thumbnail per connected display (same pattern as the per-app-window preview picker in the other mode) and let the user pick **one** display to record. No support for recording multiple displays at once/combined into a single output.
- Captured window closes mid-recording (app crash or window closed) in per-window mode: **auto-stop and save** the recording as if Stop were pressed (save to Downloads, open Finder), then **reset the app back to the first window**, same as a normal stop.
- General rule: **every path that ends a recording and saves a file** (manual Stop, or an auto-stop like the crashed/closed-window case above) must open the Downloads folder in Finder afterward — this isn't unique to the manual Stop button, it should apply consistently to any future auto-stop/error path too.
- Long recordings: split output into **1.5-hour segments** (separate files), rolling over to a new file every 1.5 hours during a single recording session. Purpose is crash/power-loss resilience (an in-progress `AVAssetWriter` file can end up unplayable if the app dies mid-write) — encoding memory itself stays flat regardless of duration since samples stream straight to disk, so segmenting isn't a memory necessity, just a resilience/file-size tradeoff.
- Code signing / notarization: **no Apple Developer ID for now** ($99/year, skipped) — ship unsigned (or ad-hoc signed) builds via GitHub Releases. Users will hit Gatekeeper warnings and need to right-click → Open (or clear the quarantine attribute) to run it. Revisit if/when distribution needs grow.
- App Sandbox: **enabled**, for defense-in-depth and user trust (this app already asks for mic/screen access, so containing its filesystem reach matters) and to keep an App Store submission possible later without retrofitting. Use the `com.apple.security.files.downloads.read-write` entitlement for direct Downloads folder access (no file picker needed), and `com.apple.security.device.audio-input` for microphone access under sandbox. Screen Recording/Microphone TCC permission prompts are separate from sandboxing and are required either way. Sandbox entitlements are embeddable in an ad-hoc signature, so this is compatible with skipping the Developer ID.
- Static security analysis: **CodeQL** runs as a separate GitHub Actions workflow (`.github/workflows/codeql.yml`, `macos-26` runner to match the build workflow) on push/PR to `main` plus a weekly schedule, building the project with `xcodebuild` (autobuild isn't reliable for Swift) and analyzing with the `swift` CodeQL language pack. Verified green on actual CI runs against `main`.
- Testing strategy: two test targets. **`RecRexUnitTests`** (scheme `RecRex`, run via `make test`) covers pure logic that doesn't need real screen/mic capture — file naming, segment rollover timing, the start-button label state machine — and is what **CI (GitHub Actions)** runs on every push/PR. **`RecRexDesktopTests`** (its own scheme, run via `make test-desktop`) actually drives `RecordingManager` against the real ScreenCaptureKit/AVFoundation stack — starts a real few-second recording, stops it, and asserts the output is a non-empty, playable MP4 with the expected tracks. It needs real Screen Recording/Microphone permission granted locally to this app's signing identity, so it's local-only and intentionally excluded from both the `RecRex` scheme and CI — the name flags that it needs a real desktop session, which GitHub's hosted runners don't provide. Any future manual QA checklist is still open.
- App name: **RecRex** (record + a little T-Rex mascot vibe) — short, no colliding app found in a search. Bundle identifier: `dev.denis1stomin.recrex`.
- Project management: the project was initially scaffolded with **XcodeGen** (`project.yml` as source of truth, generated `.xcodeproj` gitignored) to avoid `.pbxproj` merge-conflict noise. Later **converted to a normal, committed `.xcodeproj`** at the user's request — `project.yml` was deleted, `RecRex.xcodeproj` is now tracked in git directly, and CI builds against it without a generate step. `xcuserdata`/`*.xcuserstate` (per-user IDE state) stay gitignored as usual even though the project file itself is committed. Revisit the XcodeGen approach if multiple contributors start editing the project concurrently, since the merge-conflict tradeoff is what it was originally meant to avoid.

### UX flow
1. **First window** (shown on app launch) has three toggles/checkboxes:
   - Record video
   - Record system audio
   - Record microphone
   - Plus a start button whose caption depends on the video toggle:
     - Video toggled ON → button reads **"Select video source"**
     - Video toggled OFF → button reads **"Start recording only audio"**

2. **Second window** (shown only when video recording is enabled, after clicking "Select video source") — choose the video source:
   - Option A: **Record whole screen** — shows a screen selection preview
   - Option B: **Record a specific app window** — shows app window previews
   - Plus a "Start Recording" button to begin capture with the chosen source.

3. **Recording starts**: the app window hides.
   - If video is being recorded, macOS's own native screen-recording indicator takes over — the OS highlights/shows the window or screen being captured (standard system behavior, e.g. like ScreenCaptureKit's capture picker/indicator), no custom UI needed for this part.
   - If audio-only, the app just hides with no visible capture indicator beyond the standard system recording indicator (menu bar icon macOS shows for any app using the mic/screen recording).

4. **Clicking the app in the Dock, or switching to it with Cmd+Tab, while recording** opens a **processing window** showing:
   - Short description of the settings applied (what's being recorded)
   - A timer counting up from recording start
   - **Pause** button — pauses recording
   - **Stop** button — stops recording, saves the video to the **Downloads** folder, opens that folder in Finder, then returns the app to the very first window (as if just launched)
